## 1. רקע ופרסונה

נועה היא בימאית בתיאטראות בישראל ומלווה שחקנים, מרצים ואנשי במה לפיתוח קול ושיקום קול. אחת המובילות בארץ בתחום. עובדת לעיתים 12 שעות ביום, יצירתית, מתקשה לעצור.

**המצב היום:** אין CRM מסודר, אין מעקב אחרי לידים, לידים נופלים בין הכיסאות, היומן עמוס מאוד, מתקשה עם טבלאות ומספרים, לפני התחלת קמפיינים ממומנים בפייסבוק.

**המטרה:** לעבור ממצב של "אני עושה הכל לבד" למצב של "אני מנהלת את העסק ויש לי מערכת שעוזרת לי".

### ארבע קטגוריות השירות של נועה

**1. קליניקה** (אישי, אחד-על-אחד)
- פיתוח קול - מפגש בודד, ללא הגבלת מפגשים, 300 ₪ למפגש
- עמידה מול קהל - תוכנית של 8 מפגשים, 2,400 ₪
- שיקום קול ולקויות קוליות - תוכנית של 8 מפגשים, 2,400 ₪

**2. סדנאות והרצאות** (קבוצתי, ~20 איש)
- סדנת דיבור / הופעה / שפת גוף - חד-פעמי, 2,000 ₪ לשעתיים
- אומניות הבמה - 3-4 מפגשים, 6,000-8,000 ₪ לסדרה
- הרצאה לארגון / אוניברסיטה / מטפלות רגשיות - 2,000 ₪

**3. ליווי והפקות** (אישי, מתמשך)
- ליווי הפקה אישית - 3-4 חודשים, 2 ש"ש, 9,600 ₪
- בימוי הפקה גדולה בתיאטרון פרינג' - תמחור לבירור

**4. קורס דיגיטלי/היברידי** (קבוצתי, מתמשך)
- 12 מפגשים: 6 דיגיטלי, 4 זום, 2 פרונטלי/כנס
- עדיין בפיתוח - תמחור לבירור

## 2. עקרונות מנחים

- המערכת לא שולחת אוטומטית הודעות בוואטסאפ - נועה שולחת ידנית
- שכבת AI היא תומך בלבד (סיכומים, זיהוי לידים רדומים) - לא מנסחת תגובות ללקוחות
- ממשק ויזואלי, ללא טבלאות מורכבות
- פולואפ = בועת התראות בדשבורד (לא פוש מציק). פריט שלא טופל עובר ל"ממתין לטיפול" שגלוי תמיד עד סגירה ידנית
- ליד חדש שנכנס = פוש מיידי לטלגרם (זה הדבר היחיד שדורש דחיפות אמיתית)
- כל פעולה נפוצה - עד 2 לחיצות מהנייד

## 5. מודל נתונים (DB Schema)

### 5.1 טבלת `leads`

```sql
CREATE TABLE leads (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    full_name VARCHAR(200) NOT NULL,
    phone VARCHAR(20),
    email VARCHAR(200),
    organization_name VARCHAR(200),

    -- קטגוריזציה
    service_category VARCHAR(50) NOT NULL,  -- clinic / workshops / production / digital_course
    service_subtype VARCHAR(100),  -- voice_development / public_speaking / etc.

    -- מצב
    status VARCHAR(30) NOT NULL DEFAULT 'NEW',
    waiting_on VARCHAR(30) DEFAULT 'NOAH',  -- NOAH / CLIENT / ASSISTANT / ASSISTANT_PENDING_NOAH / SYSTEM / NONE
    priority_level VARCHAR(20) DEFAULT 'normal',  -- normal / hot / vip
    preferred_contact VARCHAR(20) DEFAULT 'whatsapp',  -- phone / whatsapp / email

    -- בעלות
    owner_id UUID REFERENCES users(id),

    -- צעד הבא (cache של ה-task הפעיל)
    next_action_type VARCHAR(50),
    next_action_due_at TIMESTAMPTZ,
    needs_attention BOOLEAN DEFAULT FALSE,

    -- מקור
    source_channel VARCHAR(50) NOT NULL,  -- form / email / manual / referral / facebook / etc.
    source_detail TEXT,
    utm_source VARCHAR(100),
    utm_campaign VARCHAR(100),
    utm_content VARCHAR(100),

    -- היסטוריה
    last_inbound_at TIMESTAMPTZ,
    last_outbound_at TIMESTAMPTZ,
    last_activity_type VARCHAR(50),
    reply_boost_until TIMESTAMPTZ,

    -- דגלים
    dormant_flag BOOLEAN DEFAULT FALSE,
    is_duplicate_suspected BOOLEAN DEFAULT FALSE,
    is_returning_customer BOOLEAN DEFAULT FALSE,
    pending_classification BOOLEAN DEFAULT FALSE,

    -- סגירה
    closure_reason VARCHAR(50),  -- no_response / not_relevant / price / timing / etc.

    -- הערה אישית
    personal_note TEXT,

    -- timestamps
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_leads_status ON leads(status);
CREATE INDEX idx_leads_owner ON leads(owner_id);
CREATE INDEX idx_leads_needs_attention ON leads(needs_attention) WHERE needs_attention = TRUE;
CREATE INDEX idx_leads_next_action ON leads(next_action_due_at) WHERE status NOT IN ('WON', 'LOST', 'ARCHIVED');
```

### 5.3 טבלת `tasks`

```sql
CREATE TABLE tasks (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    lead_id UUID NOT NULL REFERENCES leads(id) ON DELETE CASCADE,
    type VARCHAR(50) NOT NULL,  -- first_response / followup / proposal_followup / etc.
    assigned_to UUID REFERENCES users(id),
    due_at TIMESTAMPTZ NOT NULL,
    status VARCHAR(20) DEFAULT 'open',  -- open / done / canceled / snoozed
    snoozed_until TIMESTAMPTZ,

    created_at TIMESTAMPTZ DEFAULT NOW(),
    completed_at TIMESTAMPTZ
```

**הערה חשובה:** טבלת `tasks` היא מקור האמת לצעד הבא. השדות `next_action_type` ו-`next_action_due_at` בטבלת `leads` הם cache של ה-task הפעיל - כשנוצר/עודכן task → מעדכנים את ה-cache בליד.

## 6. סטטוסים ומעברי סטטוס

### 6.1 שמונה סטטוסים מוגדרים

| סטטוס | משמעות |
|---|---|
| `NEW` | ליד חדש שעוד לא נגעו בו |
| `IN_PROGRESS` | תהליך פעיל מולו |
| `PROPOSAL_SENT` | נשלחה הצעה, מחכים לתשובה |
| `BOOKING_PENDING` | הליד ביקש מועד, מחכה לאישור נועה |
| `BOOKED` | יש פגישה מאושרת ביומן |
| `WON` | נסגרה עסקה |
| `LOST` | נסגר ללא עסקה |
| `ARCHIVED` | לא רלוונטי / ישן / כפילות |

### 6.2 דיאגרמה

```
                    ┌──────┐
       ┌───────────►│ NEW  │◄────────┐
       │            └──┬───┘         │
       │               │ (פעולה ראשונה)│
       │               ▼              │
       │       ┌──────────────┐       │
       │       │ IN_PROGRESS  │───────┤
       │       └──┬────────┬──┘       │
       │          │        │          │
       │ (הצעה)   │        │ (בקשת מועד)
       │          ▼        ▼          │
       │  ┌─────────────┐  ┌───────────────┐
       │  │PROPOSAL_SENT│  │BOOKING_PENDING│
       │  └──────┬──────┘  └──────┬────────┘
       │         │                 │
       │         │ (סגירה/דחיה)    │ (אישור)
       │         ▼                 ▼
       │   ┌─────────┐         ┌────────┐
       └───┤ WON/LOST│◄────────┤ BOOKED │
           └─────────┘         └────────┘
                                   │
                                   ▼
                              ┌─────────┐
                              │ARCHIVED │ (אחרי זמן רב)
                              └─────────┘
```

### 6.3 חוקי מעבר

| מעבר | טריגר | תנאים |
|---|---|---|
| NEW → IN_PROGRESS | פעולה ראשונה (template_sent, call, etc.) | אוטומטי |
| IN_PROGRESS → PROPOSAL_SENT | proposal_sent | ידני |
| IN_PROGRESS → BOOKING_PENDING | meeting_requested | אוטומטי מדף תורים |
| BOOKING_PENDING → BOOKED | meeting_approved | אישור נועה |
| BOOKING_PENDING → IN_PROGRESS | meeting_rejected | ידני |
| כל סטטוס → WON | סימון "נסגרה עסקה" | ידני |
| כל סטטוס → LOST | סימון "סגור ללא עסקה" | ידני, חובה closure_reason |
| WON/LOST → IN_PROGRESS | lead_reopened | ידני |
| ARCHIVED → IN_PROGRESS | lead_reopened | ידני |

### 6.4 שינוי סטטוס אוטומטי

רוב המעברים בין סטטוסים קורים אוטומטית לפי פעולות שהיא עושה:
- לחיצה על "שלחתי תבנית" → `IN_PROGRESS`
- שליחת הצעה → `PROPOSAL_SENT`
- אישור פגישה → `BOOKED`
- סימון "סגור עסקה" → `WON`

### 6.5 חוקי ולידציה

- ליד פתוח (NEW עד BOOKED) חייב להיות לו `owner_id`
- ליד סגור (WON/LOST/ARCHIVED): אין `next_action`
- סגירה כ-LOST דורשת בחירת `closure_reason`
- אין מחיקה - רק ARCHIVED

## 7. שדות ליד

### 7.1 שדות חובה ביצירת ליד חדש

- שם מלא
- טלפון
- מקור פנייה

זה הכל. שאר הפרטים אופציונליים ומולאים בהמשך. אם רגע הכניסה דורש מאמץ - הליד לא ייכנס בכלל.

### 7.2 שדות מומלצים בכרטיס ליד

- מייל
- שם ארגון (אם רלוונטי)
- **סוג שירות** (בולט, מתחת לשם הליד) - אחת מ-4 הקטגוריות וסוג ספציפי
- סטטוס
- בעלים (נועה / עוזרת)
- מחכה ל... (לקוח / נועה / עוזרת)
- עדיפות (רגיל / חם / VIP)
- ערוץ מועדף (טלפון / וואטסאפ / מייל)
- מקור שיווקי + מקור מפורט
- תאריך פנייה
- תאריך קשר אחרון
- תאריך פולואפ הבא
- חדש / חוזר
- הערה אישית

### 7.3 תיוג ויזואלי "מחכה ל..."

- **מחכה לי (נועה)** = ברירת מחדל, אין סימון
- **מחכה ללקוח** = אייקון ⏳ קטן ליד שם הליד
- ניתן לסנן ברשימה לפי המצב

## 9. תבניות תגובה

### 9.1 עקרונות

5-10 תבניות מוכנות מראש שמכסות את סוגי הפניות הנפוצים: פתיחה לקליניקה, פתיחה לארגון, פולואפ אחרי שיחה, פולואפ אחרי הצעת מחיר, חידוש קשר לרדום, אישור פגישה, מענה אחרי שעות, ועוד.

### 9.2 תבניות עם משתנים אוטומטיים

בתוך כל תבנית יוטמעו שדות שמתמלאים אוטומטית מהכרטיס של הליד - למשל `{customer_name}`, `{service_subtype}`, `{organization}`. נועה לא צריכה לערוך כל פעם, ההודעה נראית אישית, וזמן ההכנה יורד לאפס.

### 9.3 שליחה תמיד ידנית

לחיצה על "שלח" פותחת את וואטסאפ עם הטקסט המוכן בתוך שיחה עם הלקוח. נועה רק לוחצת שלח. ככה התחושה מול הלקוח נשמרת אישית - בלי בוט שמדבר במקומה.

### 9.4 פתיחה חכמה של הודעה לפי סוג ליד

אותו רעיון של תבנית - אבל הגרסה משתנה לפי מי זה:

- ליד פרטי → תבנית קצרה, חמה, אישית
- ארגון → תבנית מקצועית יותר, עם פתיחה רשמית
- ליד רדום → פתיחה עדינה ולא לוחצת, מתאימה לחידוש קשר

## 11. תורים ודף קביעת תור

### 11.1 דף קביעת תור ללידים

הליד מקבל לינק לדף ייעודי, רואה את השעות הפנויות ביומן של נועה באופן אוטומטי, ובוחר מועד נוח לו. החל מהרגע הזה התור נכנס ליומן בסטטוס "ממתין לאישור" - נועה מקבלת התראה, ובלחיצה אחת מאשרת או מציעה מועד חלופי.

**למה זה חשוב:** נועה לא רוצה שהיומן שלה ייקבע בלי שליטה שלה, אבל גם לא רוצה לתאם תור עם כל ליד טלפונית. זה הפתרון באמצע - הליד בוחר, היא מאשרת.

### 11.2 איך זה מתחבר ליומן

כשליד נכנס לדף לבחור תור, המערכת תציע לו רק שעות שאינן מסומנות ככבר תפוסות או "חסום". אין סיכוי שתור יתנגש עם זמן ההכנה של נועה או עם פגישה אישית.

### 11.3 סטטוס תור ברור

- ביקש מועד
- ממתין לאישור נועה
- אושר
- צריך חלופה

### 11.4 מנגנון "אחרי פגישה"

30 דקות אחרי סיום אירוע, cron יוצר משימת `post_meeting_update` שתופיע בדף "פעולות היום" של נועה בכניסה הבאה למערכת. המשימה כוללת בחירה מהירה:
- ממשיכים
- לשלוח הצעה
- לקבוע סדנה
- לעקוב בעוד X זמן
- לא רלוונטי כרגע

אם לא נבחר כלום תוך 24 שעות מסיום הפגישה - המשימה ממשיכה להופיע ב"פעולות היום" עד שתטופל.

## 12. התאמות UX לעבודה מהנייד

### 12.1 כפתור "ליד חדש" צף

בכל מסך באפליקציה יש כפתור צף בפינה. לחיצה פותחת טופס מהיר עם 3 שדות בלבד: שם, טלפון, מקור.

### 12.2 פעולה הבאה ככפתור ראשי

פתיחת כרטיס ליד לא מציגה רשימת אופציות - אלא כפתור אחד גדול בראש המסך, שמשתנה לפי מצב הליד: "שלח תבנית פתיחה" לליד חדש, "שלח הצעה" לליד שהתבשל, "התקשרי" אם סומן שעדיף טלפון. המערכת מובילה לפעולה, לא מבקשת לחשוב.

### 12.3 שינוי סטטוס אוטומטי לפי פעולה

היא לוחצת "שלחתי תבנית" - הסטטוס משתנה אוטומטית מ"חדש" ל"בטיפול". פחות חשיבה, פחות תיעוד ידני.

### 12.4 תזכורת סוף יום

ב-19:00 כל יום, סיכום קצר אחד: כמה לידים טופלו, כמה ממתינים למחר, מה דחוף.

### 12.5 ליד שעונה - קופץ לראש הרשימה

ברגע שמתקבלת תשובה מליד, הוא קופץ לראש הדשבורד עם סימן ויזואלי. ליד שחוזר = ליד חם.

### 12.6 דף "פעולות היום"

בבוקר, היא לא רואה את כל המערכת - אלא רשימה ממוקדת של 5-7 דברים שצריך לעשות היום. בלי רעש.

### 12.7 העברת ליד לעוזרת בלחיצה אחת

כפתור ייעודי בכרטיס - לחיצה מעבירה את הליד לעוזרת עם הודעה אוטומטית פנימית, וסטטוס משתנה ל"באחריות עוזרת".

### 12.8 חיפוש חכם

בנייד נועה תזכור לפעמים רק "הבחור מאינטל" או "הטלפון שמסתיים ב-4821". החיפוש מוצא לפי שם, טלפון מלא, 4 ספרות אחרונות, שם ארגון, או נושא.

### 12.9 4 צבעי מצב בלבד

- 🔴 **אדום** - דחוף, דורש טיפול היום (גוון עדין, לא צועק)
- 🟠 **כתום** - דורש טיפול בקרוב (פולואפ מתקרב)
- 🟢 **ירוק** - בתהליך תקין, אין צורך לפעול עכשיו
- ⚪ **אפור** - סגור / בארכיב

**ליד תקין = שום סימון.** רק חריגות מקבלות סימון ויזואלי.

### 12.10 ארכיון שקט במקום מחיקה

שום ליד לא נמחק לצמיתות. במקום זה - סיווג: "לא רלוונטי", "סגור ללא עסקה", "כפול". בעתיד, היא תוכל לחזור ולהבין מה קרה, ואולי אפילו לחדש קשר.

### 12.11 סדר תצוגה בדשבורד

**מסך הבית = דשבורד "תמונת מצב" קטן ופשוט**

בראשו בלוק "פעולות היום" (אם יש), ומתחת הסקציות הרלוונטיות:
- אם יש פעולות היום → "5 משימות מחכות לך היום"
- אם אין → "אין משימות דחופות היום ✓" + הצגת סקציות אחרות
- מתחת: "פניות חדשות שעוד לא ענית עליהן" (אם יש)
- מתחת: בלוק קטן של "תובנות השבוע"

**סדר ברירת מחדל של לידים בתוך כל בלוק:**
1. לידים שצריכים טיפול דחוף (סימון אדום)
2. לידים חדשים שלא נגעת בהם בכלל
3. לידים שענו לאחרונה (קפיצה לראש בעקבות תגובה)
4. לידים מסומנים כ-VIP / חמים
5. לפי תאריך הפולואפ הקרוב ביותר
6. לפי תאריך עדכון אחרון (החדש קודם)

**תצוגות נוספות:**
- **כל הלידים** - ברירת מחדל לפי תאריך עדכון אחרון. פילטרים: סטטוס, צבע, בעלות, מקור, מחכה לי/ללקוח
- **פעולות היום** - ממוין לפי דחיפות (אדום → כתום), ובתוך כל קבוצה לפי וותק
- **ממתין לטיפול** - עמוד נפרד לפריטים שלא טופלו אחרי כל ההתראות
- **הצעות פתוחות** - תצוגה ייעודית להצעות שנשלחו וממתינות לתשובה

## 13. פיצ'רים חכמים שמורידים חיכוך

### 13.1 כפתור "מה עכשיו?" דינמי

בראש כל כרטיס ליד, כפתור גדול אחד שמשתנה לפי הסטטוס:

- ליד חדש → "שלח תבנית פתיחה"
- אחרי הצעה שנשלחה → "פולואפ על ההצעה"
- ליד שהתעניין → "קביעת שיחה"
- סומן כעדיף טלפון → "התקשרי"

היא לא צריכה לזכור מה לעשות. המערכת מציעה.

### 13.2 סנוז חכם בלחיצה

## 16. מנגנון התראות וצ'יפים

### 16.1 פולואפ = בועת התראות בדשבורד

תזכורות פולואפ הן בהגדרה לא דחופות - אם משהו דורש מינימום 24 שעות לפני שמתריעים עליו, אין צורך בפוש. במקום זה, בועת התראות בולטת בדשבורד מציגה את כל מה שדורש טיפול. כשהיא נכנסת בבוקר - הכל מרוכז במקום אחד.

**זרימת ההתראה:**
- פולואפ מגיע למועדו → בועת התראה בדשבורד פעם אחת
- אם לא טופל אחרי 7 ימים → עובר לעמוד נפרד "ממתין לטיפול" (לא בדשבורד הראשי)
- בעמוד "ממתין לטיפול": מיון לפי וותק, אפשרות לסגור או להעביר לארכיון בלחיצה

**פיצ'ר עתידי (פאזה 3):** אפשרות לנועה להגדיר תזכורת חוזרת (כמה פעמים, כל כמה זמן). בפאזה 1 - בועת התראה אחת + עמוד "ממתין לטיפול" מספיקים.

### 16.2 הבחנה חשובה: "לא טופלו בזמן" מול "ממתין לטיפול"

שני מושגים שונים:
- **"לא טופלו בזמן"** (תובנה שבועית, §13.9) - **כל ליד שעבר את `next_action_due_at`** ולא טופל, אפילו אם זה רק יום אחד. מטרה: לתת תמונה רחבה של ביצועי השבוע.
- **"ממתין לטיפול"** (עמוד נפרד, §22.7 `tasks/stuck`) - **רק לידים שתקועים 7+ ימים**. מטרה: לידים שדורשים פעולה דחופה, לא רעש על overdue זמני.

### 16.3 פוש לטלגרם - רק לליד חדש

הדבר היחיד שמקבל פוש מיידי הוא ליד חדש שנכנס. ההתראה הולכת לטלגרם, ולא למייל או וואטסאפ.

**למה דווקא טלגרם:** מייל ווואטסאפ מלאים ברעש - התראות שם נבלעות. טלגרם, לעומת זאת, יכול לשמש ערוץ ייחודי רק להתראות מהמערכת. הצליל והאייקון של טלגרם הופכים לסימן אחד וברור: "ליד חדש". פחות סיכוי לפספס, יותר תגובה בזמן.

### 16.4 צ'יפים מהירים לסיכום שיחה

אחרי שיחה, לא לפתוח טופס. במקום זה, כפתורי לחיצה אחת.

**6 צ'יפי ברירת מחדל:**

| צ'יפ | סטטוס לאחר לחיצה | פולואפ אוטומטי |
|---|---|---|
| אין מענה | IN_PROGRESS, waiting_on=NOAH | retry_call תוך 24 שעות |
| רוצה פרטים | IN_PROGRESS, waiting_on=NOAH | followup תוך 24 שעות |
| מעוניין בשיחה | IN_PROGRESS, waiting_on=CLIENT | followup תוך 48 שעות |
| רוצה הצעה | IN_PROGRESS, waiting_on=NOAH | send_proposal תוך 24 שעות |
| לא רלוונטי כרגע | IN_PROGRESS, waiting_on=CLIENT | dormant_check תוך 60 יום |
| לחזור בעוד חודש | IN_PROGRESS, waiting_on=CLIENT | followup תוך 30 יום |

המערכת מעדכנת סטטוס אוטומטית, קובעת פולואפ מתאים, ומתעדת בהיסטוריה.

**למה "לא רלוונטי כרגע" → IN_PROGRESS ולא LOST?** זה "לא רלוונטי **כרגע**" - חוזרים בעוד 60 יום. אם הליד באמת לא רלוונטי באופן סופי, נועה תסמן ידנית "סגור ללא עסקה" עם `closure_reason='not_relevant'`.

**הגדרה גמישה:** בהגדרות, נועה יכולה לערוך, להוסיף או להסיר צ'יפים. לכל צ'יפ אפשר להגדיר: שם, סטטוס שזה משייך אליו, waiting_on, סוג פולואפ אוטומטי, ובעוד כמה ימים.

## 17. כללי פולואפ

### 17.1 ברירות מחדל (ניתנות לשינוי על ידי נועה)

| מצב | יעד ברירת מחדל |
|---|---|
| ליד חדש שלא טופל (`first_response`) | 24 שעות |
| לקוח שהתעניין ולא סגר (`warm_followup`) | 48-72 שעות |
| הצעה לארגון (`proposal_followup`) | 3-5 ימי עסקים |
| לקוח שלא חזר (`dormant_check`) | 60-90 יום |
| ארגון שהתעניין בהרצאה | 24 שעות |

### 17.2 חישוב מדויק

- `first_response`: due = `created_at + 24h`. אם נפל ביום שאינו יום עבודה → יום עבודה הבא 09:00
- `warm_followup`: due = `last_outbound_at + 48h` (ניתן לשינוי ל-72h)
- `proposal_followup`: due = `add_business_days(last_outbound_at, 3)` (ניתן לשינוי ל-5)
- `dormant_check`: due = `last_activity_at + 60d`

### 17.3 פונקציות זמן נדרשות

יש לממש:
- `is_business_day(datetime, locale=IL)`
- `next_business_datetime(datetime)`
- `add_business_days(datetime, n)`

**הגדרת יום עבודה:**
- ראשון-חמישי
- לא כולל חגים
- שעות עבודה ניתנות להגדרה במערכת

## 20. ניהול טוקנים ב-AI

### 20.1 רקע ולקח

ב-EmailFlow זוהתה בעיה קריטית: מיילים נכנסים (במיוחד ניוזלטרים, מערכות שיווק כמו Smoove/Mailchimp, וטפסים אוטומטיים) נשלחו ל-classifier כשהם נושאים את ה-HTML הגולמי שלהם — כולל CSS inline, base64 של תמונות מוטמעות, footer של unsubscribe, ו-tracking links. התוצאה: קריאות AI שצרכו 10,000-12,000 input tokens במקום ~1,500 המצופים — פי 8 מהנדרש.

**השלכות שיש למנוע ב-Noa_Leads מראש:**

- חריגה מתקרת ה-TPM של Anthropic → דחיית בקשות (429) → לידים שלא סווגו
- עלות מנופחת — ~$0.015 למייל במקום $0.002
- סיווגים גרועים, כי ה-AI מקבל סלט של CSS עם הטקסט האמיתי קבור בתוכו

### 20.2 דרישה למימוש

כל מסלול שמעביר תוכן מייל ל-AI חייב לעבור קודם דרך פונקציית ניקוי ייעודית. אסור להעביר HTML גולמי או טקסט שחולץ ב-regex פשוט.

### 20.3 מפרט הפונקציה `clean_email_body_for_ai`

**מיקום:** `app/utils/email_cleaning.py`

```python
def clean_email_body_for_ai(
    raw_content: str,
    purpose: Literal['classification', 'summary', 'extraction'] = 'classification'
) -> str:
```

**תקרת תווים לפי purpose:**

| Purpose | Max chars | מתי משתמשים |
|---|---|---|
| classification | 1,200 | סיווג עסקי/לא עסקי, זיהוי קטגוריה |
| summary | 2,000 | סיכום תוכן, חילוץ פרטים |
| extraction | 2,500 | חילוץ נתונים מורכבים (שם, טלפון, סוג שירות) |

**שלבי הניקוי (לפי הסדר):**

1. פרסור HTML עם BeautifulSoup, parser מועדף `lxml` עם נפילה ל-`html.parser`
2. הסרת תגיות: `script`, `style`, `head`, `meta`, `link`, `noscript`
3. הסרת אלמנטים לפי class/id שמכילים אחת מהמילים: `footer`, `unsubscribe`, `tracking`, `social-links`, `preheader`, `header-logo`
4. חילוץ טקסט: `get_text(separator=' ', strip=True)`
5. החלפת URLs ארוכים: `re.sub(r'https?://[^\s]{100,}', '[link]', text)`
6. קריסת רצפי whitespace: `re.sub(r'\s+', ' ', text)`
7. הסרת שורות שמכילות רק תווי בקרה / זנב URL
8. Truncation בטיחותי לפי `purpose`. אם נחתך — להוסיף `"\n\n[הטקסט קוצר]"`

### 20.4 לוגינג מובנה

```
email_id=<id>, purpose=<...>, raw_len=<>, cleaned_len=<>, ratio=<>, truncated=<bool>
```

### 20.5 מקומות שחייבים להשתמש בפונקציה

- מסלול קליטת מייל מ-Gmail → classifier
- מסלול קליטת טופס עם שדה body
- כל מקום שמעביר טקסט חופשי ל-AI לצורך סיווג, סיכום, או הצעת תבנית

### 20.6 מה אסור

- **אסור לקרוא לפונקציה הזו על תוכן שמיועד לתצוגה ב-UI.** ל-UI יש דרישות שונות - שם משתמשים בפונקציה אחרת או מציגים את ה-HTML המקורי.
- **אסור להעביר את `MAX_BODY_CHARS` כפתרון לבד בלי BeautifulSoup.** truncation גס חותך לפני שהטקסט האמיתי מתחיל.

### 20.7 מנגנון retry על קריאות Anthropic

- **retry על שגיאות רשת זמניות** (`APIConnectionError`, `APITimeoutError`, `InternalServerError`) — כן
- **retry על `RateLimitError` — לא.** במקום זה:
  1. לתפוס את השגיאה
  2. להחזיר 503 ל-caller
  3. לשמור את הליד עם דגל `pending_classification=true`
  4. ב-job חוזר אחרי 60 שניות יטופל

### 20.8 סינון לפני AI — חיסכון של 40%+ מהקריאות

לפני שמייל מגיע ל-classifier בכלל, לבדוק heuristically:

**1. סינון לפי `From` header:**
אם השדה מכיל אחת מהמילים → לסמן כ-spam ולא לקרוא ל-AI:
- `noreply`, `no-reply`, `notifications@`, `newsletter@`, `donotreply`

**2. סינון לפי domain שולח:**
רשימה שחורה של domains של מערכות שיווק אוטומטיות:
- `mailchimp.com`, `smoove.io`, `sendgrid.net`, `constantcontact.com`, `hubspot.com`, `mandrillapp.com`

**3. סינון לפי `List-Unsubscribe` header:**
קיום ה-header הזה = סימן כמעט ודאי לניוזלטר אוטומטי.

**4. Double-check על false positives:**
יש לקוחות לגיטימיים שעוברים דרך mailchimp/sendgrid. אם המייל סווג כ-spam לפי domain, אבל בגוף המייל יש מילים שמעידות על פנייה אישית — לשלוח ל-AI בכל זאת.

מילות מפתח (regex case-insensitive):
- `פנייה`, `מעוניין`, `מעוניינת`
- `אשמח לקבוע`, `אשמח לתאם`, `אשמח להבין`
- `יש לי שאלה`, `אני מחפש`, `אני מחפשת`
- `רוצה לדעת`, `רוצה להתייעץ`

### 20.9 מדידה והפקת לקחים

אחרי שבוע ראשון של פעילות אצל נועה:
- כמה מיילים סוננו לפני AI
- ממוצע tokens לקריאת classifier
- מקסימום tokens שנצפה
- שיעור שגיאות 429 (אמור להיות 0)
- עלות AI יומית

**יעדים:**
- ממוצע מתחת ל-1,500 input tokens לקריאה
- אפס דחיות rate limit
- עלות AI יומית מתחת ל-$0.50 בנפחי הלידים של נועה

### 20.10 שמירת הטקסט המקורי

גם אחרי הניקוי, לשמור את ה-HTML המקורי במסד הנתונים (בשדה נפרד). זה לתצוגה למשתמש, debug, ולמקרה שנרצה לעבד מחדש בעתיד עם אלגוריתם משופר.

```
email_messages:
  - raw_html (לתצוגה ול-debug)
  - cleaned_text (מה שנשלח ל-AI)
  - cleaning_metadata (purpose, ratio, truncated, timestamp)
```

מערכת מרכזית, דשבורד, כרטיסי לידים, תבניות תגובה, פולואפ, מענה אוטומטי לשעות לא פעילות, תיוג מקור, ובעלות בסיסית בין נועה לעוזרת. בסוף השלב הזה - יש לה מערכת עובדת ושלמה.

### מה לא נכלל

קל לעוף רחוק מדי. אלה דברים ששווים בעתיד אבל לא עכשיו - אחרי שה-flow הבסיסי עובד יציב:

- מערכת ניקוד לידים אוטומטית
- אוטומציות "אם-אז" מורכבות
- בוטים שעונים אוטומטית ללקוחות
- זיהוי כפילויות חכם (שווה לחזור אליו כשמתחילים קמפיינים)
- דוחות BI מתקדמים

**הסיבה:** המטרה בשלב הזה היא לא "CRM עשיר" - אלא תגובה בזמן, סדר, ובעלות ברורה על הצעד הבא. אחרי שזה עובד, כל פיצ'ר נוסף נכנס על בסיס יציב.
